# Actors: Alia and agents

Everything Alia does is done by an **actor**, and every actor acts either **for a
person** (on that person's data) or **as itself** (on its own Oxy account). This
page is the map; each section ends with the doc that holds the detail and the code
where it is decided. The binding decisions are
[ADR 0015](./adr/0015-actors-and-identities.md) and, for what an actor is in code,
[ADR 0034](./adr/0034-gemies-and-alia.md).

**Every actor is a gemie: an `agents` row.** Alia is one too — the official, global
gemie `ALIA_GEMIE_ID` (`domain/alia-gemie.ts`, seeded by migration 0135) — and a turn,
conversation, call or task that names no gemie is hers (`lib/alia-gemie.ts`). What
makes her different is the configuration of her row, never a `null` agent or her id:

| Attribute (`agents`) | Alia | Every other gemie (the default) | What it decides |
|---|---|---|---|
| `memory_store` | `nilo` | `gemie` | Whose memory of the person: Nilo's (`oxy_nilo_memories__*`, answer settings, writing style) or its own `agent_memory_documents` |
| `reach` | `person` | `grants` | The person's own assistant (Oxy's person lane, every connected account and agent of the person, their installed skills, their name and Inbox context, the base identity, no remit) or a persona under its grants, linked skills and remit |
| `mailbox` | `false` | `true` | Whether its own Oxy account is a working one (`self_*` tools, own-mailbox alerts) |
| `task_authority` | `standing` | `session` | Tasks under standing authority on `alia-tasks`, no agent session; her chats are loose and her thread with a person is one `agent_threads` row. Or durable sessions, and every conversation with the person is a stretch of its thread |
| `capability_grants` | no `computer`, no `browser` | its owner's | Its fixed families; Alia has no machine |

## The two actors

| | For the person (their data) | As itself (its own account) |
|---|---|---|
| **Alia** — one for everybody, the default | Every Oxy app of the person, read and act, with no permission prompts and no "connect" step. Authority: the person present in the turn, or the task's standing authority in the background. | Oxy account "alia": a public identity with no mailbox. |
| **An agent** — a persona a person creates | Every live own-app tool on the verified requester's account; no per-app levels. | Its own Oxy `bot` account: its own Inbox, its own sign-ups on websites. No grant needed. |

**Alia** is the assistant everyone gets: the orchestrator that answers, remembers,
runs tasks and reaches the person's Oxy apps the way a mail assistant reads its
owner's mail. Nobody has to create or pick an agent to use any of that.

Her Oxy account is not there yet: Oxy reserves the username `alia` and models her as
the actor `{ type: 'alia', ownerAccountId }`, with no account (Oxy contract). Until
Oxy creates her gemie's account (ADR 0034 phase 2), her row's `oxy_account_id` holds
`ALIA_PENDING_OXY_ACCOUNT_ID`, which Oxy resolves to nobody, and her Oxy calls keep
speaking that lane through the one seam that chooses it, `lib/gemie-oxy-actor.ts`.
The public wire still spells her as no `agentId` (`publicAgentId`), so a chat with
her looks exactly as it did until the routes take the Gemies vocabulary. Her row is
public (everybody uses it) but not listed in the catalogue or in `searchAgents` until
that account exists: a card with no name would be a regression.

**Her thread.** Besides her loose chats (each one a conversation of its own, like
ChatGPT's) and voice, a person has one continuous thread with her, the same mechanism
every gemie's thread is (`lib/gemie-thread.ts`): one `agent_threads` row per person,
whose stretches carry its id in `conversations.agent_thread_id`. A loose chat carries
none, so the two never mix. She has no handle yet, so the thread is opened by her
gemie id (`GET /agents/:id/thread`). A turn in it is a turn of her gemie like any
other: Nilo memory, the person's reach, her tools, standing authority and no agent
session.

**An agent** is optional. It is an Oxy `bot` account owned by the person who
created it; Alia stores only its runtime (prompt, model, archetype, marketplace
listing). It has its own capability grants (deny by default), its own memory, its
own computer and its own mailbox.

- Detail: [Agents](./agents.md) — "An agent IS an Oxy `bot` account".
- Code: `lib/agent-identity.ts`, `lib/agent-account.ts` (`packages/api/src/`).

## Who is in the turn decides what is reachable

[ADR0022](./adr/0022-first-party-platform-authority.md) defines own platform
access. `requesterAccountId` identifies the person whose data `oxy_*` reaches.
The owner and anybody else using a public agent each receive their OWN apps.
The agent's owner is never substituted for a missing requester.

| Turn | `oxy_*` account | `self_*` account |
|---|---|---|
| Alia or agent with a person present | Verified effective requester | Bot only when that requester operates it |
| Goal/background work | Original Oxy task root requester | Same bot/operator rule checked live |
| Nested agent | Same task root and requester; separate actor | No access to an unrelated bot owner |
| Structured automation | Original operation's exact account/resource | Only when explicitly bound |

Own service identity is an attested workload. The shared SDK carries requester
proof and operation tickets; no user bearer is persisted. Agent reach and app
confinement remain separate checks. See `lib/tool-pipeline.ts`,
`lib/tools/oxy-services.ts`, and `lib/oxy-task-authority.ts`.

## Permissions

Own Oxy apps need no connection, scope grant or agent app-level setting. The
live catalogue selects available tools; product ownership, membership,
entitlements and operation limits authorize their effects. An unavailable
operation returns `oxy_app_unavailable`, never advice to connect an own app.
External MCP/OAuth connections and other Alia capability families retain their
existing configuration. The historical app-level table has no runtime readers
or writers and does not grant access.

## No agent asks for approval

This migration adds no approval prompt. Existing product constraints, bounded
operations, R0–R3 runtime policy and threat-detector blocking stay in force.
Asking for missing information with `askUserQuestion` remains an ordinary
question. See [Governance](./agents.md#governance).

## Background work: every task has an actor, Alia by default

A task (`/automations`) always has a responsible actor. `actorSelection` omitted
means `{ mode: 'fixed', agentId: ALIA_GEMIE_ID }` (`automation_definitions.actor_mode`:
`fixed` or `automatic`; the `alia` mode was retired by 0135–0139). Nobody has to pick an
agent.

- **Alia's tasks** (a gemie with `task_authority = 'standing'`) run unattended on the
  `alia-tasks` queue (`lib/alia-task-queue.ts`, `lib/alia-task-run.ts`, which loads the
  gemie recorded on the run) and post their result into the task's own conversation.
  They use **standing Oxy authority** asked for when the task is saved with the
  owner present (`provisionAliaTaskAuthorizations` in `lib/automation-authority.ts`).
- **Watches** make a recurring "tell me when X changes" cheap: each tick is a hashed
  Clarity read, and only a change queues an Alia run (`lib/alia-watch.ts`).
- **Abandoned Alia runs** are failed and refunded by `lib/alia-task-reaper.ts`,
  inside the agent run reaper's sweep (`lib/agent/run-reaper.ts`).
- **An agent's unattended runs** are durable sessions (lease + reaper, ADR 0011)
  whose Oxy calls go through Oxy's agent-run authorizations.

- Detail: [Background work and proactive outreach](./proactive-intelligence.md).

## Writing first

Alia and agents may start a conversation, within a budget: at most 3
own-initiative messages a day per person and actor, none while the actor's last 2
are unanswered (`lib/agent/outreach-budget.ts`).

- **An important email.** Alia tells the person about their own Inbox (in her
  outreach conversation, `lib/agent/alia-outreach.ts`); an agent tells its owner
  about its OWN mailbox (in their thread, `lib/agent/agent-outreach.ts`). The email
  is untrusted; the classifier sees sender, subject and snippet only, and the
  message is a fixed template (`lib/proactive/email-outreach.ts`). The switch is per
  actor (`GET|PUT /notifications/email-alerts`).
- **Results and check-ins** from agents' background runs, and their own follow-ups.

- Detail: [Background work → Writing first](./proactive-intelligence.md#writing-first-an-important-email),
  [Agents → An agent writing first](./agents.md#an-agent-writing-first).

## Memory is per actor

Alia (`memory_store = 'nilo'`) remembers the person in Nilo, with her answer settings
and writing style in `user_memories`; each other gemie (`memory_store = 'gemie'`)
remembers them separately in `agent_memory_documents` (MEMORY.md plus topic files, per
gemie and person). A turn of any other gemie never receives Alia's memory or her
memory tools: the catalogue declares them for Oxy's person lane only, and the assembler
drops them for any gemie whose store is not Nilo (`lib/tool-pipeline.ts`;
`alia-gemie-guarantees.test.ts`). The person sees, edits
and forgets an agent's in that agent's editor (`GET|PUT|DELETE /agents/:id/memory`); Alia's
lives in Nilo (Settings → Memory says so and opens it). Memory in a prompt is data, never
instructions (`memoryDataBlock`, `lib/memory/memory-prompt.ts`).

- Detail: [Memory](./memory-system.md), [Agents → Memory is per actor](./agents.md#memory-is-per-actor).

## The agents' computer

An agent with the `computer` grant has its own Linux machine and a real browser:

- One gVisor container per agent and person (`agent:<agentId>:user:<oxyUserId>`),
  no network for the shell, a persistent `/workspace`.
- A persistent Chromium context per actor behind a validating egress proxy, so a
  sign-in survives the browser closing and the host sleeping.
- GemiesOS (`packages/gemies-os`) is a Spot instance that stops itself when
  idle; the API wakes it on demand (`lib/computer/host-waker.ts`).
- The person watches it live and can take control (agent page → Computer,
  `routes/agents/computer.ts`, `packages/app/src/features/agents/ui/computer/`).
- Alia herself has no computer: her row holds no `computer` grant, and her work never
  runs on an agent runtime (`task_authority = 'standing'`); the tools are built only for
  an agent's runtime turn (`lib/agent/actions.ts`) and only when `GEMIES_OS_URL`
  is set.

- Detail: [Agents → The agent's computer](./agents.md#the-agents-computer-computer).
- Operations: `OxyHQ/oxy-infra` `docs/runbooks/47-gemies-os.md`;
  infrastructure `terraform-uswest2/gemies-os.tf`.
