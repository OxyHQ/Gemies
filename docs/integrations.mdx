# Integrations and tools

Alia's reach comes from four layers:

1. **Native tools** in `packages/api/src/lib/tools/`, assembled per turn by one
   pipeline (`ToolPipeline.forUser`, `lib/tool-pipeline.ts`).
2. **Oxy apps** — every app of the Oxy ecosystem, first party, built from Oxy's
   signed capability catalogs.
3. **Connectors** — remote MCP servers a person connects: the providers' own, curated, the hundreds
   synced from the official MCP Registry, and their own by URL. No connector runs code of ours
   against a provider's API, and none runs on our hosts.
4. **Channel integrations** — long-running connectors in `packages/integrations/`
   for Telegram, WhatsApp and Discord. A person's own WhatsApp or Telegram account is
   theirs, connected once in Settings and granted to the gemies that may use it, at most one of
   which answers on it ([connected accounts](#connected-accounts)).

Which of these an actor may use is in [Actors: Alia and agents](./actors.mdx).

## Native tools

An agent's tools are partitioned by capability family (`FIXED_FAMILY_TOOLS` in
`domain/capability-grants.ts`, deny by default); Alia's own turns are not limited
by a grant. The families and the tools each contributes:

| Family | Tools |
|--------|-------|
| `web` | `webSearch`, `webScraper`, `deepResearch`, `getWeather`, `getMarketQuote`, `getFairCoin` |
| `browser` | `browser` — the runner's Clarity primitive (`search`, `goto`, `get_text`); no Chromium |
| `artifacts` | `canvas`, `generateFile` |
| `memory` | `memory` (the agent's own MEMORY.md and topic files), `searchThread` |
| `automation` | `createAutomation` |
| `delegation` | `createAgent`, `searchAgents`, `delegate` |
| `computer` | `computer_*`, `run_computer_command`, `*_computer_file(s)`, `browser_*` — the agents' computer ([agents](./agents.md#the-agents-computer-computer)) |
| `mcp:<id>`, `agent[:<id>]`, … | instanced families: one connector or agent per grant (`consultAgent` for `agent`) |
| the person's account grant (`ACCOUNT_GRANTED_TOOLS`) | `listAccountChats`, `readAccountMessages`, `sendAccountMessage`, `sendTelegramMessage` (to the person, through a Telegram they granted the gemie) — not a family: the [connected accounts](#connected-accounts) the person granted the turn's gemie |
| no grant (`UNGRANTED_TOOLS`) | `getCurrentDate`, `getDeviceInfo`, `planPreview`, `plan`, `suggestNewConversation` |

### The canvas

`canvas` (`lib/tools/canvas.ts`) draws content for the person instead of writing it in the
reply: `markdown` (a report or document), `deck`, `dashboard`, `chart`, `table`, `code`,
`form`, `image` and `artifact`. A deck is `{ slides: [{ title, subtitle?, bullets?, body?, notes? }] }`
and a dashboard `{ widgets: [stat | chart | table | text] }`; both are validated when the tool
runs, and a malformed one comes back to the model as an `error` naming the field, so a surface
never receives one it cannot draw. Surfaces open them on their own: the SDK's
`CanvasComponent` draws every type in the app's panel, and Astro opens reports, decks and
dashboards in a tab with comments, versions (a later call with the same title and type) and
exports.

Alia's memory tools (Nilo's `oxy_nilo_memories__*`, declared for `alia` only) are hers
alone and are never offered to an agent ([memory](./memory-system.md)). The 128-tool request limit and the
`loadTools` tool loader are in [chat runtime](./chat-runtime.mdx#tool-budget-and-the-tool-loader).

Risk is classified per call by `classifyActionRisk` (`lib/agent/governance.ts`):
`R2` runs flagged, `R3` is blocked, and nothing asks for approval — see
[governance](./agents.md#governance).

### Adding a tool

1. Write the tool constructor in `packages/api/src/lib/tools/` and export it from
   `lib/tools/index.ts`.
2. Put it in a capability family in `domain/capability-grants.ts`, or argue it into
   `UNGRANTED_TOOLS` (the list is meant to stay short).
3. Assemble it in `ToolPipeline.forUser` (`lib/tool-pipeline.ts`), the only assembler.
4. Make sure `classifyActionRisk` gives it the right class.
5. Test it under `lib/tools/__tests__/`; `lib/__tests__/capability-grants.test.ts`
   fails if a family's grant reaches nothing.

## Connectors

A connector is a **remote MCP server** reached over streamable HTTP (or SSE) at an `https` URL: a
provider's own server from the curated catalogue (Notion, Linear, Slack…, `lib/mcp-registry.ts`), a
server synced from the official MCP Registry or Docker's MCP catalogue into the store
([the synced store](#the-synced-store)),
or a server the person adds by URL. Nothing runs on our servers against a provider's API, and nothing
is started as a process: a server that is only a package (`npx`, a container, stdio) is never offered.
Integrations (`packages/integrations/src/mcp/`) is the MCP client: it connects, keeps the OAuth tokens
and calls the tools.

- **Where it is reached.** Every request a connector makes — the transport, OAuth discovery, token
  exchange and refresh, revocation — goes through `mcp/connector-fetch.ts`, the SDK's `safeFetch`:
  each hop's address is resolved and refused when it is private, loopback, link-local or the cloud
  metadata service, and the connection is pinned to the address that was judged. Only `https`.
- **A curated connector is the catalogue's.** It is reached at the catalogue's address with the
  catalogue's OAuth settings whatever its row says (`lib/mcp-connector-config.ts`), so an edited URL
  never receives a client Gemies holds for a provider. A synced connector is reached at the address it
  was connected at, with its own sign-in (none, or OAuth with Dynamic Client Registration); Gemies
  holds nothing for it, and it stays the person's when the store stops offering it. A custom
  connector is the person's: its URL and, optionally, a header (an API key);
  `mcp_servers_transport_check` admits only `sse` and `streamable-http`. Only a custom connector's
  address can be edited.
- **Several accounts of one connector.** Each Connect is a new account and its own row, written when
  its OAuth completes (`mcp_oauth_states.registry_id` carries the entry until then), so the connected
  list never holds a half-made one. Each account has its own slug (`notion`, `notion_2`), its own
  tools (`mcp_notion__search`, `mcp_notion_2__search`, described `[Notion · ana@acme.com] …`) and its
  own grant (`mcp:<id>`). **Which account a tool acts on is explicit**: the model chooses it by the
  tool it calls, and a gemie sees only the accounts it was granted; Alia sees every one. The account
  is named by the provider's OpenID Connect claims when its token response carries them
  (`account-label.ts`), otherwise "Account 2" and on, and the person can rename it.
- **Logos.** `lib/connector-logos.ts` reads each logo from, in order: the server's own
  `serverInfo.icons` (MCP `initialize`, spec 2025-11-25; a provider answers it only with a token, so
  it is read on connect, and a store server that needs no sign-in publishes it to its health check),
  the entry's MCP Registry icons (a curated entry's `mcpRegistryName`, a synced entry's own listing),
  and the website's brand mark (`apple-touch-icon`, an SVG or PNG icon, `/favicon.ico`). Each image
  is fetched through `safeFetch`, recognized by its bytes (PNG, JPEG, WebP, GIF, ICO, SVG), capped at
  256 KiB and stored in `connector_logos` under its SHA-256; the app loads it only from
  `GET /mcp/logos/:id` on the API's origin (immutable, `nosniff`, a sandboxing CSP), never from a
  provider. The store's job keeps every offered entry's logo, a bounded round an hour, each read
  again after a week; `mcp_registry_logos.source` and `source_url` say where each came from. No logo
  is a monogram.
- **Tool descriptions are somebody else's text.** Before a connector's tools reach the model, each
  description is made plain text and cut to 1,024 characters (`lib/untrusted-text.ts`: no zero-width,
  bidirectional or Unicode-tag characters, no `<IMPORTANT>`-like tags), and the base prompt says a
  connector's descriptions and results are data, never instructions (`prompts/base.md`).

### Routes

| --- | --- |

### The apps

The UI is the SDK's (`@gemies/sdk/connectors`), drawn by the Gemies and the Alia apps alike:
`GemieConnectorsStore` is the **Connectors** store, a page of its own at `/connectors`: a search,
the categories with their counts, the Official, Verified and No sign-in filters, the order (Featured,

`GemieConnectedConnectors` is **Settings › Connected**, only what the person connected, with each account's state, who uses it,
Reconnect, Rename and Disconnect; `ConnectorLogo` is the one logo every screen draws (the store,
Settings, a gemie's editor, the composer's pick and a tool step in the chat). A web sign-in returns
to `/connectors`, which finishes it; a native one finishes in the auth session.

(local only), and the reference servers that only run as a local command (filesystem, PostgreSQL,
SQLite, memory).

The scopes requested are the entry's `oauth.scope`: the least a provider documents (Atlassian's
`*:agent-interface` scopes and never `delete:`/`manage:`; Zoom's without deletes; Slack's user-token
search, read and post scopes; Work IQ's `WorkIQAgent.Ask`, `WorkIQ.Read`, `WorkIQ.Act`).

**Tools.** A connector's tools are the provider's, named `mcp_<slug>__<tool>`; read and write tools
are both offered, and no tool asks for approval ([ADR 0020 §3](./adr/0020-every-agent-is-the-same-agent.md#3-no-agent-asks-for-approval)):
an MCP tool runs flagged (`R2`).

**Tokens.** OAuth tokens and a DCR client are stored encrypted in integrations'
`mcp_connector_auths` (`mcp/oauth-provider.ts`); an issued client is read from the API's environment
on every call and sent over the internal transport, never stored with a connector. A sign-in left
unfinished for an hour is forgotten when the person starts another (`forgetAbandonedAuthorizations`).
A connector that lost its session in a deploy reconnects from its stored authorization on the next
call; one whose authorization is gone shows "Needs reconnecting".

**Disconnecting** (`DELETE /mcp/:id`) asks integrations to revoke first
(`POST /mcp/servers/:id/revoke`): the provider's RFC 7009 endpoint (advertised, or the one the
registry documents) gets the refresh and the access token, and the stored row is deleted whatever the
provider answered. The connector row goes only after that answered; if integrations cannot be reached
the API answers `502 revoke_failed` and the person retries.

### The synced store

Beside the curated catalogue, the store offers the remote MCP servers of two public catalogues, copied
into `mcp_catalogue_entries` with their provenance (`source`, `upstream_name`, `upstream_version`) by
one leader-gated job (`lib/connector-catalogue/`, lease `connector-catalogue`, every hour):

- the **official MCP Registry** (`registry.modelcontextprotocol.io`, `official-registry.ts`), the
  primary source: every server's latest version, a page of 100 at a time with a pause between;
- **Docker's MCP catalogue** (`github.com/docker/mcp-registry`, MIT, `docker-catalogue.ts`): its
  `type: remote` entries, read from one archive of the repository. Docker reviews every entry, so its
  servers carry the `verified` badge; an endpoint the official registry already lists is not taken
  from Docker (`earlier_source` in its report), so one server is listed once.

Both are read into one shape (`ListedServer`) and judged by the same policy, gates and health check.

1. **Sync** (`sync.ts`, each source when its last complete pass is older than 12 hours, the registry
   first): a failed page asked again twice, and a 429 honoured until its `Retry-After`
   (`mcp_catalogue_sync_state.retry_after`, per source). A pass that fails changes nothing; a complete one inserts new servers (`pending`), updates changed ones (a new
   endpoint is `pending` again), marks those no longer listed `removed_at` and brings back those
   listed again. `mcp_catalogue_sync_state.last_report` keeps its counts, refusals by reason included.
2. **Health check** (`health.ts`, up to 3,000 a round, 16 at a time (a first sync of 28,000 servers is checked within a day), never-checked and best-proven first):
   integrations' `POST /mcp-catalogue/probe` (`packages/integrations/src/mcp/probe.ts`, through
   `connectorFetch`, for no account, 15 s) `initialize`s the server without a token. One that answers
   lists its tools (`tools/list`): offered with sign-in `none` unless its tools hide characters, carry
   instructions to the model ("ignore previous instructions", `<IMPORTANT>`…), or list none. One that
   answers 401 has its OAuth metadata read (RFC 9728, RFC 8414): offered with `oauth` when it takes
   Dynamic Client Registration, otherwise `needs_provider_app` and not offered. One failure is checked
   again within the hour; the second in a row makes it `failing`. Healthy servers are checked again
   every 3 days, failing ones every 7. If integrations cannot be asked the round stops and changes
   nothing. An OAuth server's tools are known only once a person connects it.
3. **Logos** of every offered entry ([logos](#connectors), above).

**What is taken** (`policy.ts`): an active server with a streamable HTTP (preferred) or SSE remote
at an `https` URL, with no `{template}` and no header its catalogue marks required (a Docker header
naming a secret is required unless the secret says `required: false`); never a package (stdio, `npx`,
a container, an image Docker runs). Left out: a registry publisher with more than 25 such servers (a
listing farm; the registry holds publishers with thousands; on 2026-11-13 the 54 namespaces past it
were all generated wrappers of other companies' APIs or aggregators, and the big vendors' namespaces,
Microsoft's 12 the largest, were all under it, so no `allowBulk` is set), a server the curated catalogue already has (same
endpoint or same registry name: a synced server never overrides a curated one), and every listing of
one endpoint but the best-proven, most recent one. Names and descriptions are the registry's,
made plain text and cut (`lib/untrusted-text.ts`); a category is read from their words.

**Badges.** The registry has no "verified" flag: a server's name is the proof of who published it
(a reverse-DNS namespace through DNS or HTTP, `io.github.<login>` through GitHub), and the registry
does not check that a remote is on the proven domain. So the store says `official` when a proven
domain's server is reached on that domain (`com.notion/mcp` at `mcp.notion.com`; every curated entry
is official), `verified` when it is reached elsewhere or Docker's reviewed catalogue lists it, and
`community` for a GitHub namespace.

**The operator's say** is `CATALOGUE_OVERRIDES` in `policy.ts`, reviewed like code, keyed by a
server's registry name, `host:<host>` (and every host under it) or `publisher:<namespace>`: `hide`
(the denylist: Smithery's shut-down proxies `server.smithery.ai` and `run.tools` are in it),
`allowBulk`, `category`, `trust` and `featured`. A hidden server leaves the store on the next deploy;
connections people already made to it are theirs and keep working until they disconnect them.

**Sources considered** (2026-11-13). Only the official registry is synced: its terms dedicate the
registry data to the public domain (CC0 1.0, §10) and let subregistries copy, enrich and process it
(§11) without implying a partnership (§6); its API needs no key and documents no rate limit, and it
asks aggregators to poll regularly but infrequently, never per user request
([registry aggregators](https://modelcontextprotocol.io/registry/registry-aggregators.md),
[terms](https://modelcontextprotocol.io/registry/terms-of-service.md)). [Docker's MCP registry](https://github.com/docker/mcp-registry) (MIT, about 75 reviewed remote
servers) is the second source. Not synced:
[Glama](https://glama.ai/policies/terms-of-service) (needs a key; its licence requires a credit on
every page and forbids a competing directory), [PulseMCP](https://www.pulsemcp.com/api/docs/v0.1)
(partners only, no public terms), [Smithery](https://smithery.ai/future) (its API and proxies shut
down on 2026-10-31; its URLs are its own proxies, not providers'), [mcp.so](https://mcp.so/terms-of-service)
(no API, claims its content), GitHub's MCP registry (a curated mirror of the official one, under
GitHub's terms only) and the awesome-mcp-servers lists (repositories, not remote endpoints). Adding
a source is a new `MCP_CATALOGUE_SOURCES` value, a reader into `ListedServer` and its place in
`CATALOGUE_SOURCES` (`sync.ts`).

## Oxy apps

Oxy apps are **first party**. Alia and Oxy are the same ecosystem, so there is no
"connect your inbox" or authorize step: Alia reaches every Oxy app of the person
present in the turn. An agent uses that same requester even when its owner is
somebody else; its separate bot account is explicitly selected as `self_*` ([actors](./actors.mdx)).

Each app registers one signed capability catalog in Oxy; Alia builds its tools from
that registry. Adding an app requires a catalog and handlers in the app, not
app-specific code in Alia.

- Oxy owns catalog registration, delegations and live authorization decisions.
- `packages/api/src/lib/tools/oxy-services.ts` turns catalog tools into AI SDK tools,
  named `oxy_<app>__<tool>` (the person's account) and, for an agent,
  `self_<app>__<tool>` (its own account).
- A tool whose catalogue `actors` excludes the current actor (`alia`, or `agent` for
  both of an agent's identities) is never offered: the Oxy profile reads are
  `requester`-only, and Oxy refuses anyone else (`tool_not_available_to_actor`).
  Absent `actors` means `alia` + `agent`. `lib/tools/oxy-catalog-actors.ts` reads
  the field whichever `@oxy.so/contracts` is installed (older ones refuse it).
- One registry catalogue that does not parse is logged and skipped; it costs that
  app's tools, never the others'.
- `packages/api/src/lib/oxy-capability-authority.ts` exchanges the turn's authority
  (a verified direct requester, an original durable task, or an automation's stored authorization)
  for opaque execution-authorization ids and short-lived tickets.
- When Oxy cannot confirm authority the model receives `oxy_app_unavailable` (or
  `oxy_app_result_unknown` when an effect's outcome is unknown) with a fixed
  sentence, never Oxy's raw reason, and is told not to route around it.
- Each call carries one idempotency key per tool call (`idempotencyKey` in
  `oxy-services.ts`); Inbox's catalog 2.0.0 takes it only from that header, not
  from a model-written argument.
- Each catalogue says how its internal tools are reached (`internalTransport`):
  `mcp` is `<internalBaseUrl>/_oxy/mcp`, pinned to the exact registration it was
  read from; absent or `http` is each tool's advertised invocation. See
  [Oxy application authority](./oxy-capability-boundaries.md).

Inbound service events go through `POST /webhooks/oxy`:

- The Oxy service bearer is verified centrally; Alia stores no per-app HMAC secret.
- The publisher may emit only events declared by a catalog it owns.
- `(appId, eventId)` is deduplicated before matching automations.
- Observation records actor/action decisions with no execution.
- Execution requires every declared resource/tool authorization, then obtains a
  short-lived capability ticket for the fresh run and step.
- Inbox's `new_email` also feeds important-email outreach
  ([background work](./proactive-intelligence.md#writing-first-an-important-email)).

User sessions are never forwarded to apps or retained by background runs. The
app receives only a one-minute capability ticket with its exact audience,
resource, actor, account, run, step and tool.

## Channel integrations

`packages/integrations` is a separate Express service that owns long-lived connections to messaging platforms. It mirrors channel messages into Alia conversations and exposes outbound tools the runtime can call.

| Subdirectory | Channel | Notes |
|--------------|---------|-------|
| `telegram/` | Telegram | The one Bot API layer (ADR 0037): Telegram Business through the shared bot, and gemies' own bots |
| `accounts/whatsapp/` | WhatsApp Web | Multi-device bridge with chat / message sync |
| `bots/discord-bot/` | Discord | Bot user that mirrors guild channels |
| `browser/` | Headless browser sessions | Not the gemies' computers (that is GemiesOS, `packages/gemies-os`); the API's web tools read pages through Clarity |
| `terminal/` | PTY sessions | Streamed to their owner over `/ws` |
| `realtime/` | The `/ws` WebSocket server | Subscription auth and broadcasting for terminal and browser sessions |

Inbound messages arrive at the API as either:

- **Channel-bound conversations** — each chat becomes a conversation scoped to that channel and a user, so the autonomy loop can reuse the same context graph
- **Oxy application events** — authenticated service publishers send normalized events to
  `/webhooks/oxy`, where structured automations match explicit app, event and resource fields

### Connected accounts

A person's WhatsApp and Telegram accounts are theirs (ADR 0035 as amended). They connect each one
ONCE, in Settings › Connected accounts, several per platform if they like, and then choose:

- **Which gemies may use it** (`connected_account_grants`): any gemie they may act as, and Alia,
  each with a switch. A granted gemie reads and sends through the account when the person asks it
  or a task of theirs needs it. The grant is the person's, on their account, never a capability
  grant on the gemie's row (no `messaging` family: a gemie's owner cannot grant somebody else's
  account, and Alia's one row could not hold every person's choice).
- **Which ONE answers it on its own** (`answers`, at most one per account), or none. It replies to
  what arrives as the account's replies say; with none, nothing arriving is answered. Choosing a
  gemie grants it the account too.

The same grants show from the gemie's side: its editor lists the person's accounts with a switch
each ("Accounts it can use", the same `GrantSwitchRow` its connectors use) and opens Settings to
connect more, and Alia's locked editor shows the same list (`viewer.mayGrantAccounts`). What stays
per gemie is its own Telegram bot ([below](#telegram-on-the-bot-api)).

- **One contract** between the API and the gateway, for every platform
  (`@gemies/server/internal` `accounts.ts`): platforms, the session status vocabulary, chats,
  messages and inbound metadata. The integrations service serves it through ONE router
  (`accounts/gateway-router.ts`) over an `AccountGateway` per platform (`whatsapp/gateway.ts`,
  `telegram/business/gateway.ts`), mounted at `/accounts/<platform>`, and `GET /accounts/platforms`
  says which ones run (Telegram needs the shared bot, `TELEGRAM_BOT_TOKEN`). The API offers only
  those. The gateway knows sessions, never gemies.
- **Telegram is Telegram Business** (ADR 0037). The panel's link opens the shared Gemies bot with
  a one-time code, and the person adds the bot in Telegram › Settings › Telegram Business ›
  Chatbots (Telegram Premium; private chats only). The connection never expires here: turned off
  in Telegram it is `paused` and resumes by itself, and every change is told to the API at once
  (`POST /channel-accounts/session`). The Bot API has no chat list or history, so the tools read
  what arrived since it was connected, and write only where the contact wrote in the last 24 hours
  and Telegram granted "Reply to messages".
- **Who it answers.** The account's answering gemie, and its `replies` (everyone, the chosen chats,
  or nobody) and `group_replies` (never, or when the message mentions or replies to the account).
  The gateway asks `POST /channel-accounts/inbound` before a message reaches a turn: it is answered
  only when a gemie answers the account and `shouldAnswer` says so; otherwise it gets no reply at
  all. The same call records the account's last activity. The turn is the answering gemie's
  (`middleware/channel-auth.ts` reads it from the grants), authorised as unattended work, with the
  account's Oxy task, whose actor is that gemie (`oxyActorFor`) and which moves when the person
  chooses another; an account no gemie answers holds no task, and a turn on it is refused.
- **Live status.** Listing the accounts asks the gateway for each session and stores what moved,
  so an account unlinked from the phone shows `logged-out`, not `connected`.
- **Tools.** `listAccountChats`, `readAccountMessages` and `sendAccountMessage`
  (`lib/tools/accounts.ts`), and `sendTelegramMessage`, offered only over the connected accounts the
  person granted the turn's gemie. The model names an account by a key (`whatsapp`, `whatsapp_2`,
  `telegram`) whose description says which account it is and whether this gemie answers it on its
  own or only acts when asked.
- **Failures the panel can read.** A gateway that cannot be reached or refuses answers
  `503 { error, code: 'accounts_gateway_unavailable' }` (never a `502`, which the CDN serves without
  CORS headers), a platform this deployment does not run `409 platform_unavailable`; the panel
  shows either with a Retry.
- **Order of a release.** The web app deploys only after the API's release of the same commit
  (`deploy-frontends.yml` runs on `Deploy to AWS`). The API and the integrations service deploy
  independently: `GET /accounts/platforms` is the handshake, so an API newer than its gateway
  offers nothing to connect until the gateway speaks the same contract.
- **Routes**, all the caller's own (`routes/me-accounts.ts`; anybody else's account is `404`):
  `GET /me/accounts` (the accounts with `gemieIds` and `answeringGemieId`, the `gemies` they can be
  granted to, the `platforms`), `POST /me/accounts { platform }` (connect one; answers its first
  code), `PATCH /me/accounts/:accountId { answeringGemieId?, replies?, replyChatIds?,
  groupReplies? }`, `PUT|DELETE /me/accounts/:accountId/gemies/:gemieId` (grant or revoke; a gemie
  the caller may not grant is `404|403 gemie_not_grantable`, and revoking the answering one revokes
  the task), `GET /me/accounts/:accountId/qr|chats`, `POST /me/accounts/:accountId/reauthorize`
  (renew the answering gemie's task; `409 no_answering_gemie` without one) and
  `DELETE /me/accounts/:accountId` (the gateway logs the session out and deletes what it synced).
  Deleting a gemie revokes the task of every account it answered; its grants cascade, and the
  accounts stay their people's (`lib/connected-accounts.ts`).
- **The apps.** The UI is the SDK's (`@gemies/sdk/accounts`): `GemieConnectedAccounts` is Settings ›
  Connected accounts in the Gemies and the Alia apps alike, and `GemieAccountGrants` is the
  editor's list.

Outbound tools (e.g. `sendTelegramMessage`, `sendAccountMessage`) are `R2`: they run, flagged. Structured automation actions remain bound by their exact Oxy authority and Alia risk policy.

### Telegram on the Bot API

Telegram runs on its official Bot API only, in one layer in `packages/integrations/src/telegram/`
(ADR 0037): one client (`bot-api.ts`), one webhook and inbox, one sender.

- **Webhook.** Every bot's is `${API_BASE_URL}/webhooks/telegram/<botId>`. The public API relays the
  delivery untouched to the private integrations process (`POST /telegram/updates/:botId`, as the
  API workload), which checks Telegram's `secret_token` (derived per bot from its id and
  `TOKEN_ENCRYPTION_KEY`, never stored), writes the update to `telegram_updates` and only then
  answers. A sweep at startup and every minute handles what a restart left. Every webhook is
  registered at startup and checked with `getWebhookInfo` every ten minutes.
- **The shared bot** (`TELEGRAM_BOT_TOKEN`) carries Telegram Business: a person's own Telegram as
  one of their [connected accounts](#connected-accounts), granted to their gemies.
- **A gemie's own bot** is a card of the gemie's editor (`/agents/:id/telegram-bot`): the owner
  pastes a @BotFather token, and the bot shows the gemie's name, description, tagline and picture,
  and follows them by itself: the edit that changes one marks the bot behind
  (`lib/gemie-telegram-bot-profile.ts`), and after a short debounce (an editor's autosaves become one
  update) the API gives the bot the new profile through the integrations process. Only the parts
  that changed are set, the photo only when the look or the colour changed (Telegram rate-limits
  profile updates), drawn on the server with Bloom's `renderAgentAvatarPicture` (the character in its
  colour, on a much lighter tint of it, centred for the circular crop) and rasterized on the service's
  Chromium. A failure is kept for the editor, which shows it with a retry, and retried with a backoff
  or after Telegram's `retry_after`; the run reaper's minute sweep picks up what a dying instance left.
  The API keeps the bot and its encrypted token (`bots`) and runs every turn
  (`POST /channel-bots/telegram/:botId/messages`); the integrations process reads the bots it
  speaks as (`GET /channel-bots/telegram`). A private chat is always answered; a group only when the
  bot is mentioned, named in a command or replied to (`group_replies`), and in privacy mode a bot
  sees only replies and commands. Each chat is one of the gemie's conversations. The gemie's
  balance pays first, then the person who connected the bot if they allowed it.
- **The bot recognises its person** (ADR 0037, amendment). In the editor, the person who connected
  the bot taps *Link my Telegram* (`POST /agents/:id/telegram-bot/link`): it mints, with their
  session, a durable Oxy task in which they are the effective account and the gemie the actor
  (`bots.oxy_task_id`), and opens `t.me/<bot>?start=<code>`. Telegram sends `/start <code>`; the
  API redeems the one-time code (stored only as a hash, 15 minutes) for the Telegram account that
  sent it (`bots.linked_telegram_user_id`). From then on their **private** messages from that
  account answer `personTurn`, and the integrations process runs them through `/alia/chat` as the
  verified `gemie_bot` channel identity (`x-alia-channel-bot` + `x-alia-platform-user`, resolved
  again by `middleware/channel-auth.ts`): the same turn as in the app — their Oxy apps such as
  Inbox, the gemie's granted accounts and connectors, its memory of them, skills, the session
  runtime (`scheduleFollowUp`, `continueInBackground`, browser, computer), `createAutomation`,
  billed to them. Everyone else, and the person in a group, is a third party: the gemie's public
  tools only, run in the API with nobody's authority, and the prompt says how the person links.
  Unlinking (`DELETE …/link`) or removing the bot revokes the task.
- **The gemie writes back in the chat.** Whatever the gemie posts on its own into one of its bot's
  conversations (`postAgentMessage`: a follow-up's result, a scheduled task's result, a check-in)
  is also sent there as the bot (`POST /telegram/bots/send` of the integrations process). A task
  created in a conversation delivers each result to it (`inputs.deliverTo`, set by the server from
  the turn), so a reminder asked on Telegram arrives on Telegram.

### What a channel message carries

Every channel (a gemie's own bot, Telegram Business, WhatsApp) reads a message into one shared model,
`GemieChannelMessage` in `@gemies/server` (`telegram/inbound.ts`, `accounts/whatsapp/inbound.ts`),
and the API turns it into the turn's user message the same way for all of them
(`lib/channel-messages.ts`):

- **Media is kept like an app attachment**: as a private Oxy file of the person whose conversation it
  is (`storeChannelMedia`), with a `file` part in the stored message. A photo (Telegram's largest
  size), a sticker (its image, emoji and set; an animated one by its still) and a document are the
  file; a video, a round video or a GIF is its first frame. Documents are read as attachments are
  (`readFileForModel`); a type no model reads is named, not kept.
- **A voice note or audio is transcribed** on the dictation path (`transcribeDictation`, on the account
  whose turn it is), and its transcript travels with its file part (`transcript`), so a later turn
  reads it without the audio being heard again.
- **Everything else is words**: a location or venue (with a map link), a contact, a poll, a die, the
  message it replies to (quoted), who it was forwarded from, and a kind that cannot be read ("A
  game"). What could not be fetched (over the per-file 5 MB or per-message 7 MB cap, or a failed
  download), kept or transcribed is said in the message; nothing is dropped.
- **Media is read on the turn it arrived; later turns read it in words** (`turnContentText`: the text,
  and a line per file with its transcript). A turn through `/alia/chat` (a connected account's, or a
  bot's person's) resends the whole stored conversation unchanged, parts included, so the saver
  appends to it; as a channel turn it reads only its newest message's files, with the channel's task
  (`filePartsOf(…, { latestTurnOnly })`), and is given earlier ones in words.
- **Who prepares it.** A connected account's gateway asks `POST /channel-accounts/messages` for the
  content, and a gemie bot's answer carries it (`personTurn.content`, stored under the Telegram
  message's id) or runs the third party's turn with it. The media is kept as the person who
  connected the account or the bot.
- **A gemie's own bot** also takes edits (`edited_message`: the stored message's words follow, nothing
  is answered again), can react to the message with an emoji in a third party's turn
  (`reactToMessage`, set with `setMessageReaction`), and sends an image an answer shows
  (`![alt](https://…)`) as a photo, as the shared Business bot does.

### Channel task migration (source pending rollout)

New bot links and personal messaging connections create an Oxy task while the
actual requester is signed in. Only `oxy_task_id` is retained. The gateway checks
its workload identity and the current platform/session binding, then supplies
local account context plus the task id; it never invents a user session. Unlink
and logout revoke that root before clearing the binding.

The additive `0107_first_party_task_authority` migration defaults existing channels
to `reauth_required`. It does not promote legacy links. On a controlled Alia server,
`bun dist/db/migrate-channel-tasks.js --target-database=<actual-name>`
reports candidate counts without mutation; `--apply` validates each legacy bot
`metadata.sessionToken` through Oxy's task API against the stored original person
and live link. A valid shared session creates a task and the bearer is removed.
An expired/rejected session is purged and remains `reauth_required`; transient
outages retain the candidate for retry. Concurrent unlink/relink revokes a newly
created root rather than attaching it to another person. Reports contain counts,
never bearer material. Existing connections without original requester proof remain typed inactive until
the account is next present in its normal Oxy session. Listing that account
automatically calls the owner-checked task renewal endpoint, with no new consent
button or provider reconnect. External OAuth connections and messages are preserved. This procedure has not been run in
production. Deploy the Oxy task reader and published SDKs first, then the Alia
schema and code, then perform the verified conversion and account-level readback.

### Workload readiness and development

API and integrations construct `OxyServer` with the shared `/server/aws`
`createAwsWorkloadCredentialProvider`. Credential resolution is lazy, so a valid
SSO/assumed role in a development shell is supported without an ECS-only env guard.
The provider accepts temporary credentials with a session token and expiry; static
IAM user keys and product API keys are not substitutes. Readiness requires a token
mint against the intended environment's active workload binding and the recipient's
`oxy-service:<applicationId>` audience, not merely a configured API URL. Keep each
process role distinct even when API and integrations share an application id.

## CrowdSource moderation delivery

Alia's durable moderation outbox uses the published CrowdSource SDK factory with
Alia's existing OxyServer. The factory owns the canonical recipient audience and
refresh; the shared temporary IAM provider also supports local role/SSO sessions.
No Oxy customer key, static service key or caller-selected tenant substitutes for
the workload. One process client is reused and disposed on reset. Delivery flags,
idempotent outbox rows and the external CrowdSource webhook signature remain
independent of this identity change. Deploy this producer only after the
CrowdSource workload reader is verified live.
