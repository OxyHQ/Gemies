# Integrations and tools

Alia's reach comes from four layers:

1. **Native tools** in `packages/api/src/lib/tools/`, assembled per turn by one
   pipeline (`ToolPipeline.forUser`, `lib/tool-pipeline.ts`).
2. **Oxy apps** — every app of the Oxy ecosystem, first party, built from Oxy's
   signed capability catalogs.
3. **Connectors** — providers' own remote MCP servers a person connects, and their own MCP servers
   by URL. No connector runs code of ours against a provider's API.
4. **Channel integrations** — long-running connectors in `packages/integrations/`
   for Telegram, WhatsApp and Discord. A person's own WhatsApp or Telegram account is
   linked to ONE gemie, which answers on it ([connected accounts](#connected-accounts)).

Which of these an actor may use is in [Actors: Alia and agents](./actors.mdx).

## Native tools

An agent's tools are partitioned by capability family (`FIXED_FAMILY_TOOLS` in
`domain/capability-grants.ts`, deny by default); Alia's own turns are not limited
by a grant. The families and the tools each contributes:

| Family | Tools |
|--------|-------|
| `web` | `webSearch`, `webScraper`, `deepResearch`, `getWeather`, `getMarketQuote`, `getFairCoin` |
| `browser` | `browser` — the runner's Clarity primitive (`search`, `goto`, `get_text`); no Chromium |
| `artifacts` | `canvas`, `generateFile` |
| `memory` | `memory` (the agent's own MEMORY.md and topic files), `searchThread` |
| `messaging` | `sendTelegramMessage` (to the person, through the Telegram they linked to the gemie), `listAccountChats`, `readAccountMessages`, `sendAccountMessage` |
| `automation` | `createAutomation` |
| `delegation` | `createAgent`, `searchAgents`, `delegate` |
| `computer` | `computer_*`, `run_computer_command`, `*_computer_file(s)`, `browser_*` — the agents' computer ([agents](./agents.md#the-agents-computer-computer)) |
| `mcp:<id>`, `agent[:<id>]`, … | instanced families: one connector or agent per grant (`consultAgent` for `agent`) |
| no grant (`UNGRANTED_TOOLS`) | `getCurrentDate`, `getDeviceInfo`, `planPreview`, `plan`, `suggestNewConversation` |

### The canvas

`canvas` (`lib/tools/canvas.ts`) draws content for the person instead of writing it in the
reply: `markdown` (a report or document), `deck`, `dashboard`, `chart`, `table`, `code`,
`form`, `image` and `artifact`. A deck is `{ slides: [{ title, subtitle?, bullets?, body?, notes? }] }`
and a dashboard `{ widgets: [stat | chart | table | text] }`; both are validated when the tool
runs, and a malformed one comes back to the model as an `error` naming the field, so a surface
never receives one it cannot draw. Surfaces open them on their own: the SDK's
`CanvasComponent` draws every type in the app's panel, and Astro opens reports, decks and
dashboards in a tab with comments, versions (a later call with the same title and type) and
exports.

Alia's memory tools (Nilo's `oxy_nilo_memories__*`, declared for `alia` only) are hers
alone and are never offered to an agent ([memory](./memory-system.md)). The 128-tool request limit and the
`loadTools` tool loader are in [chat runtime](./chat-runtime.mdx#tool-budget-and-the-tool-loader).

Risk is classified per call by `classifyActionRisk` (`lib/agent/governance.ts`):
`R2` runs flagged, `R3` is blocked, and nothing asks for approval — see
[governance](./agents.md#governance).

### Adding a tool

1. Write the tool constructor in `packages/api/src/lib/tools/` and export it from
   `lib/tools/index.ts`.
2. Put it in a capability family in `domain/capability-grants.ts`, or argue it into
   `UNGRANTED_TOOLS` (the list is meant to stay short).
3. Assemble it in `ToolPipeline.forUser` (`lib/tool-pipeline.ts`), the only assembler.
4. Make sure `classifyActionRisk` gives it the right class.
5. Test it under `lib/tools/__tests__/`; `lib/__tests__/capability-grants.test.ts`
   fails if a family's grant reaches nothing.

## Connectors

A connector is a **provider's own hosted MCP server** (Notion, Linear, Slack…), reached over
streamable HTTP and authorized by the person through OAuth, or a remote MCP server the person adds by
URL. Nothing runs on our servers against a provider's API, and nothing is started as a process: the
catalogue (`lib/mcp-registry.ts`) lists only providers' official remote servers, and a provider
without one is not in it. Integrations (`packages/integrations/src/mcp/`) is the MCP client: it
connects, keeps the OAuth tokens and calls the tools.

- **Where it is reached.** Every request a connector makes — the transport, OAuth discovery, token
  exchange and refresh, revocation — goes through `mcp/connector-fetch.ts`, the SDK's `safeFetch`:
  each hop's address is resolved and refused when it is private, loopback, link-local or the cloud
  metadata service, and the connection is pinned to the address that was judged. Only `https`.
- **A catalogue connector is the catalogue's.** It is reached at the catalogue's address with the
  catalogue's OAuth settings whatever its row says (`lib/mcp-connector-config.ts`), so an edited URL
  never receives a client Gemies holds for a provider. A custom connector is the person's: its URL
  and, optionally, a header (an API key); `mcp_servers_transport_check` admits only `sse` and
  `streamable-http`.
- **Several accounts of one connector.** Each Connect is a new account and its own row, written when
  its OAuth completes (`mcp_oauth_states.registry_id` carries the entry until then), so the connected
  list never holds a half-made one. Each account has its own slug (`notion`, `notion_2`), its own
  tools (`mcp_notion__search`, `mcp_notion_2__search`, described `[Notion · ana@acme.com] …`) and its
  own grant (`mcp:<id>`). **Which account a tool acts on is explicit**: the model chooses it by the
  tool it calls, and a gemie sees only the accounts it was granted; Alia sees every one. The account
  is named by the provider's OpenID Connect claims when its token response carries them
  (`account-label.ts`), otherwise "Account 2" and on, and the person can rename it.
- **Logos.** `lib/connector-logos.ts` reads each logo from, in order: the server's own
  `serverInfo.icons` (MCP `initialize`, spec 2025-11-25; providers answer it only with a token, so it
  is read on connect), the entry's record in the official MCP Registry (`mcpRegistryName`), and the
  provider website's brand mark (`apple-touch-icon`, an SVG or PNG icon, `/favicon.ico`). Each image
  is fetched through `safeFetch`, recognized by its bytes (PNG, JPEG, WebP, GIF, ICO, SVG), capped at
  256 KiB and stored in `connector_logos` under its SHA-256; the app loads it only from
  `GET /mcp/logos/:id` on the API's origin (immutable, `nosniff`, a sandboxing CSP), never from a
  provider. A leader-gated job reads the catalogue's logos daily (`connector-logo-refresh.ts`);
  `mcp_registry_logos.source` and `source_url` say where each came from. No logo is a monogram.

### Routes

| Route | What |
| --- | --- |
| `GET /mcp/registry` | The store: the entries this deployment can connect, with their logos. An entry whose issued client or approval is missing is not listed. |
| `POST /mcp/connect { registryId, returnTo }` | A new account: `{ authorizationUrl }`. |
| `POST /mcp/custom { name, url, headers?, returnTo }` | A custom server: connected at once, or `{ authorizationUrl }` when it answers 401 (`authorization_required`). |
| `GET /mcp/installed` | What the person connected: each account, its status, logo and `usedBy` (Alia, and the gemies granted it). |
| `POST /mcp/:id/reconnect` | Authorize an account again. |
| `PATCH /mcp/:id { accountLabel?, config? }` | Rename the account; a custom server's URL and headers. |
| `DELETE /mcp/:id` | Disconnect (below). |
| `GET /mcp/oauth/callback`, `POST /mcp/oauth/complete` | The OAuth return: the callback hands `state` and `code` to the app that started the flow (`returnTo`, checked by `lib/connector-return.ts`: a page of a trusted origin or the `gemies://`/`alia://` scheme), which finishes with its own session. |
| `GET /mcp/logos/:id` | A stored logo. |

### The apps

The UI is the SDK's (`@gemies/sdk/connectors`), drawn by the Gemies and the Alia apps alike:
`GemieConnectorsStore` is the **Connectors** store (search, categories, logos, Connect or Add account,
Add a custom MCP server), a page of its own at `/connectors`; `GemieConnectedConnectors` is
**Settings › Connected**, only what the person connected, with each account's state, who uses it,
Reconnect, Rename and Disconnect; `ConnectorLogo` is the one logo every screen draws (the store,
Settings, a gemie's editor, the composer's pick and a tool step in the chat). A web sign-in returns
to `/connectors`, which finishes it; a native one finishes in the auth session.

Not offered, because the provider has no remote MCP server a public app may use: **Google**
(Gmail, Drive, Calendar — Google's own servers are a Workspace Developer Preview that public apps may
not use before general availability; add them here as issued-client entries then), **Brave Search**
(local only), and the reference servers that only run as a local command (filesystem, PostgreSQL,
SQLite, memory).

The scopes requested are the entry's `oauth.scope`: the least a provider documents (Atlassian's
`*:agent-interface` scopes and never `delete:`/`manage:`; Zoom's without deletes; Slack's user-token
search, read and post scopes; Work IQ's `WorkIQAgent.Ask`, `WorkIQ.Read`, `WorkIQ.Act`).

**Tools.** A connector's tools are the provider's, named `mcp_<slug>__<tool>`; read and write tools
are both offered, and no tool asks for approval ([ADR 0020 §3](./adr/0020-every-agent-is-the-same-agent.md#3-no-agent-asks-for-approval)):
an MCP tool runs flagged (`R2`).

**Tokens.** OAuth tokens and a DCR client are stored encrypted in integrations'
`mcp_connector_auths` (`mcp/oauth-provider.ts`); an issued client is read from the API's environment
on every call and sent over the internal transport, never stored with a connector. A sign-in left
unfinished for an hour is forgotten when the person starts another (`forgetAbandonedAuthorizations`).
A connector that lost its session in a deploy reconnects from its stored authorization on the next
call; one whose authorization is gone shows "Needs reconnecting".

**Disconnecting** (`DELETE /mcp/:id`) asks integrations to revoke first
(`POST /mcp/servers/:id/revoke`): the provider's RFC 7009 endpoint (advertised, or the one the
registry documents) gets the refresh and the access token, and the stored row is deleted whatever the
provider answered. The connector row goes only after that answered; if integrations cannot be reached
the API answers `502 revoke_failed` and the person retries.

## Oxy apps

Oxy apps are **first party**. Alia and Oxy are the same ecosystem, so there is no
"connect your inbox" or authorize step: Alia reaches every Oxy app of the person
present in the turn. An agent uses that same requester even when its owner is
somebody else; its separate bot account is explicitly selected as `self_*` ([actors](./actors.mdx)).

Each app registers one signed capability catalog in Oxy; Alia builds its tools from
that registry. Adding an app requires a catalog and handlers in the app, not
app-specific code in Alia.

- Oxy owns catalog registration, delegations and live authorization decisions.
- `packages/api/src/lib/tools/oxy-services.ts` turns catalog tools into AI SDK tools,
  named `oxy_<app>__<tool>` (the person's account) and, for an agent,
  `self_<app>__<tool>` (its own account).
- A tool whose catalogue `actors` excludes the current actor (`alia`, or `agent` for
  both of an agent's identities) is never offered: the Oxy profile reads are
  `requester`-only, and Oxy refuses anyone else (`tool_not_available_to_actor`).
  Absent `actors` means `alia` + `agent`. `lib/tools/oxy-catalog-actors.ts` reads
  the field whichever `@oxy.so/contracts` is installed (older ones refuse it).
- One registry catalogue that does not parse is logged and skipped; it costs that
  app's tools, never the others'.
- `packages/api/src/lib/oxy-capability-authority.ts` exchanges the turn's authority
  (a verified direct requester, an original durable task, or an automation's stored authorization)
  for opaque execution-authorization ids and short-lived tickets.
- When Oxy cannot confirm authority the model receives `oxy_app_unavailable` (or
  `oxy_app_result_unknown` when an effect's outcome is unknown) with a fixed
  sentence, never Oxy's raw reason, and is told not to route around it.
- Each call carries one idempotency key per tool call (`idempotencyKey` in
  `oxy-services.ts`); Inbox's catalog 2.0.0 takes it only from that header, not
  from a model-written argument.
- Each catalogue says how its internal tools are reached (`internalTransport`):
  `mcp` is `<internalBaseUrl>/_oxy/mcp`, pinned to the exact registration it was
  read from; absent or `http` is each tool's advertised invocation. See
  [Oxy application authority](./oxy-capability-boundaries.md).

Inbound service events go through `POST /webhooks/oxy`:

- The Oxy service bearer is verified centrally; Alia stores no per-app HMAC secret.
- The publisher may emit only events declared by a catalog it owns.
- `(appId, eventId)` is deduplicated before matching automations.
- Observation records actor/action decisions with no execution.
- Execution requires every declared resource/tool authorization, then obtains a
  short-lived capability ticket for the fresh run and step.
- Inbox's `new_email` also feeds important-email outreach
  ([background work](./proactive-intelligence.md#writing-first-an-important-email)).

User sessions are never forwarded to apps or retained by background runs. The
app receives only a one-minute capability ticket with its exact audience,
resource, actor, account, run, step and tool.

## Channel integrations

`packages/integrations` is a separate Express service that owns long-lived connections to messaging platforms. It mirrors channel messages into Alia conversations and exposes outbound tools the runtime can call.

| Subdirectory | Channel | Notes |
|--------------|---------|-------|
| `telegram/` | Telegram | The one Bot API layer (ADR 0037): Telegram Business through the shared bot, and gemies' own bots |
| `accounts/whatsapp/` | WhatsApp Web | Multi-device bridge with chat / message sync |
| `bots/discord-bot/` | Discord | Bot user that mirrors guild channels |
| `browser/` | Headless browser sessions | Not the gemies' computers (that is GemiesOS, `packages/gemies-os`); the API's web tools read pages through Clarity |
| `terminal/` | PTY sessions | Streamed to their owner over `/ws` |
| `realtime/` | The `/ws` WebSocket server | Subscription auth and broadcasting for terminal and browser sessions |

Inbound messages arrive at the API as either:

- **Channel-bound conversations** — each chat becomes a conversation scoped to that channel and a user, so the autonomy loop can reuse the same context graph
- **Oxy application events** — authenticated service publishers send normalized events to
  `/webhooks/oxy`, where structured automations match explicit app, event and resource fields

### Connected accounts

A person links their own WhatsApp or Telegram account to one gemie, from that gemie's editor
(ADR 0035). The account is the gemie's: what arrives on it is answered by that gemie, and only that
gemie's turns for that person can use it.

- **One contract** between the API and the gateway, for every platform
  (`@gemies/server/internal` `accounts.ts`): platforms, the session status vocabulary, chats,
  messages and inbound metadata. The integrations service serves it through ONE router
  (`accounts/gateway-router.ts`) over an `AccountGateway` per platform (`whatsapp/gateway.ts`,
  `telegram/business/gateway.ts`), mounted at `/accounts/<platform>`, and `GET /accounts/platforms`
  says which ones run (Telegram needs the shared bot, `TELEGRAM_BOT_TOKEN`). The API offers only
  those.
- **Telegram is Telegram Business** (ADR 0037). The panel's link opens the shared Gemies bot with
  a one-time code, and the person adds the bot in Telegram › Settings › Telegram Business ›
  Chatbots (Telegram Premium; private chats only). The connection never expires here: turned off
  in Telegram it is `paused` and resumes by itself, and every change is told to the API at once
  (`POST /channel-accounts/session`). The Bot API has no chat list or history, so the tools read
  what arrived since it was connected, and write only where the contact wrote in the last 24 hours
  and Telegram granted "Reply to messages".
- **Who it answers.** Each account has `replies` (everyone, the chosen chats, or nobody) and
  `group_replies` (never, or when the message mentions or replies to the account). The gateway asks
  `POST /channel-accounts/inbound` before a message reaches a turn (`shouldAnswer`); a message it is
  not to answer gets no reply at all. The same call records the account's last activity.
- **Live status.** Listing the accounts asks the gateway for each session and stores what moved,
  so an account unlinked from the phone shows `logged-out`, not `connected`.
- **Tools.** `listAccountChats`, `readAccountMessages` and `sendAccountMessage`
  (`lib/tools/accounts.ts`), offered only when the turn's gemie has a connected account of the
  person, with the platform limited to those it has.
- **Alia's editor.** `GET /agents/:id` says what the caller may do (`viewer.mayEdit`,
  `viewer.mayManageAccounts`). Every person may manage their own accounts on Alia
  (`isPersonsOwnAssistant`), and nobody but Oxy may change who she is (her account has no
  act-as holder, so `PATCH /agents/:id` refuses). The Gemies app opens her editor from her sidebar
  row and her chat's header with her identity as text and only the accounts card.
- **Failures the panel can read.** A gateway that cannot be reached or refuses answers
  `503 { error, code: 'accounts_gateway_unavailable' }` (never a `502`, which the CDN serves without
  CORS headers), a platform this deployment does not run `409 platform_unavailable`; the panel
  shows either with a Retry.
- **Order of a release.** The web app deploys only after the API's release of the same commit
  (`deploy-frontends.yml` runs on `Deploy to AWS`). The API and the integrations service deploy
  independently: `GET /accounts/platforms` is the handshake, so an API newer than its gateway
  offers nothing to link until the gateway speaks the same contract.
- **Routes**, all under the gemie and for whoever may act as it (every person, for Alia):
  `GET|POST /agents/:id/accounts`, `PATCH /agents/:id/accounts/:accountId` (who it answers),
  `GET /agents/:id/accounts/:accountId/qr|chats`, `POST /agents/:id/accounts/:accountId/reauthorize`,
  `DELETE /agents/:id/accounts/:accountId` (the gateway logs the session out and deletes what it
  synced). Deleting a gemie ends its accounts' sessions and revokes their tasks first
  (`lib/gemie-accounts.ts`).

Outbound tools (e.g. `sendTelegramMessage`, `sendAccountMessage`) are `R2`: they run, flagged. Structured automation actions remain bound by their exact Oxy authority and Alia risk policy.

### Telegram on the Bot API

Telegram runs on its official Bot API only, in one layer in `packages/integrations/src/telegram/`
(ADR 0037): one client (`bot-api.ts`), one webhook and inbox, one sender.

- **Webhook.** Every bot's is `${API_BASE_URL}/webhooks/telegram/<botId>`. The public API relays the
  delivery untouched to the private integrations process (`POST /telegram/updates/:botId`, as the
  API workload), which checks Telegram's `secret_token` (derived per bot from its id and
  `TOKEN_ENCRYPTION_KEY`, never stored), writes the update to `telegram_updates` and only then
  answers. A sweep at startup and every minute handles what a restart left. Every webhook is
  registered at startup and checked with `getWebhookInfo` every ten minutes.
- **The shared bot** (`TELEGRAM_BOT_TOKEN`) carries Telegram Business: a person's own Telegram as
  a [connected account](#connected-accounts) of a gemie.
- **A gemie's own bot** is a card of the gemie's editor (`/agents/:id/telegram-bot`): the owner
  pastes a @BotFather token, and the bot takes the gemie's name, description, tagline and picture.
  The API keeps the bot and its encrypted token (`bots`) and runs every turn
  (`POST /channel-bots/telegram/:botId/messages`); the integrations process reads the bots it
  speaks as (`GET /channel-bots/telegram`). A private chat is always answered; a group only when the
  bot is mentioned, named in a command or replied to (`group_replies`), and in privacy mode a bot
  sees only replies and commands. Each chat is one of the gemie's conversations. The gemie's
  balance pays first, then the person who connected the bot if they allowed it.

### Channel task migration (source pending rollout)

New bot links and personal messaging connections create an Oxy task while the
actual requester is signed in. Only `oxy_task_id` is retained. The gateway checks
its workload identity and the current platform/session binding, then supplies
local account context plus the task id; it never invents a user session. Unlink
and logout revoke that root before clearing the binding.

The additive `0107_first_party_task_authority` migration defaults existing channels
to `reauth_required`. It does not promote legacy links. On a controlled Alia server,
`bun dist/db/migrate-channel-tasks.js --target-database=<actual-name>`
reports candidate counts without mutation; `--apply` validates each legacy bot
`metadata.sessionToken` through Oxy's task API against the stored original person
and live link. A valid shared session creates a task and the bearer is removed.
An expired/rejected session is purged and remains `reauth_required`; transient
outages retain the candidate for retry. Concurrent unlink/relink revokes a newly
created root rather than attaching it to another person. Reports contain counts,
never bearer material. Existing connections without original requester proof remain typed inactive until
the account is next present in its normal Oxy session. Listing that account
automatically calls the owner-checked task renewal endpoint, with no new consent
button or provider reconnect. External OAuth connections and messages are preserved. This procedure has not been run in
production. Deploy the Oxy task reader and published SDKs first, then the Alia
schema and code, then perform the verified conversion and account-level readback.

### Workload readiness and development

API and integrations construct `OxyServer` with the shared `/server/aws`
`createAwsWorkloadCredentialProvider`. Credential resolution is lazy, so a valid
SSO/assumed role in a development shell is supported without an ECS-only env guard.
The provider accepts temporary credentials with a session token and expiry; static
IAM user keys and product API keys are not substitutes. Readiness requires a token
mint against the intended environment's active workload binding and the recipient's
`oxy-service:<applicationId>` audience, not merely a configured API URL. Keep each
process role distinct even when API and integrations share an application id.

## CrowdSource moderation delivery

Alia's durable moderation outbox uses the published CrowdSource SDK factory with
Alia's existing OxyServer. The factory owns the canonical recipient audience and
refresh; the shared temporary IAM provider also supports local role/SSO sessions.
No Oxy customer key, static service key or caller-selected tenant substitutes for
the workload. One process client is reused and disposed on reset. Delivery flags,
idempotent outbox rows and the external CrowdSource webhook signature remain
independent of this identity change. Deploy this producer only after the
CrowdSource workload reader is verified live.
